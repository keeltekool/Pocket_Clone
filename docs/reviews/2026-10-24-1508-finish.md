### R2 [Important] Save and bucket-create wait on the agent dispatch, which can take longer than the 30 s function limit
- Where: src/lib/sorter.ts:15 (`timeout: 20_000, maxRetries: 1`); src/lib/items.ts:88 and src/app/api/buckets/route.ts:34 (both awaited); `maxDuration = 30` at src/app/api/items/route.ts:6, src/app/api/save/route.ts:5 and src/app/api/buckets/route.ts:9.
- Failure: when the Anthropic API is slow, a save takes 8 s for the page fetch plus 20 s, a retry, and another 20 s (about 49 s). Vercel kills the function after the row is inserted:
  - The app shows `Couldn't save. Try again.` and the iPhone Shortcut shows an error, but the link *was* saved. Retrying gives a duplicate.
  - The item is left with `sortAttempts = 0`.
  - Bucket create returns an error after the bucket and the `created` suggestion were already written, so a retry gets 409.
- Fix: send the response first and run the dispatch afterwards (`after(() => dispatchSort(n))` from `next/server`, the same for `dispatchBucketCreated`). Or cut the SDK to `timeout: 8_000, maxRetries: 0`.
- Confidence: CONFIRMED (the arithmetic), PLAUSIBLE (it needs a slow API)

### R3 [Important] The main page won't render until every stuck-item retry has been dispatched, one after another
- Where: src/app/page.tsx:21 → src/lib/sorter.ts:68-71
- Failure: each claimed item awaits `sortSession` in turn, up to about 41 s each. If the API is slow and 3 items are stuck, opening `/` shows a blank page for about 2 minutes.
  - The same happens when the client fetches `GET /api/items` after a login (`maxDuration` 30). That gets a 504, `.catch(() => {})` swallows it, and the page shows `Loading…` forever (Main.tsx:54-60).
- Fix: claim the items in the request, but start their sessions after the response (`after()`). Never await them on the render path.
- Confidence: CONFIRMED

### R4 [Important] The poll's `changedSince` comes from the client's clock, so a phone or laptop clock that runs ahead misses every update
- Where: src/components/Main.tsx:100
- Failure: after the first poll, `since = clientNow − 1 s`. If the device clock is 3 s ahead of the server, every `sortedAt` the agent writes falls before `since`. The card stays `Sorting…` until a reload, and polling never stops.
  - A poll that takes more than about 1 s has the same effect, because it waits on the parallel `/api/suggestions` call: a write that lands during the request is lost. Cold starts make that likely.
  - The plan's note says "a 10 s back-window on start covers small skews". That is wrong: the window only applies to the first poll.
- Fix: have `GET /api/items` return the server's `now`, taken before the query, and use it as the next `since`.
- Confidence: CONFIRMED

### R5 [Important] The stuck rule measures from `createdAt`, not from the last dispatch
- Where: src/lib/sorter.ts:59 (`createdAt + sortAttempts × 10 min < now()`)
- Failure, two cases:
  - An item with `sortAttempts = 0` counts as overdue at once. That happens while a save's dispatch is still running, or after the R2 timeout. Any page load claims it, so two sessions run for the same link.
  - A retry claimed more than 20 min after the save is overdue again straight away. The next load (another device, or a reload) turns it Unsorted seconds after the second session started. The spec's "10 minutes" for the retry never applies.

  The flow at scripts/check-ui-flows.mjs:185-187 hits this case (the second reload turns `Stuck_1` Unsorted) but only checks `sort_attempts`, so it passes. The comment at sorter.ts:54 ("10 min after the last dispatch") doesn't match the code.
- Fix: record the dispatch time on the claim and on `dispatchSort`, for example by setting `sortedAt = now()` (the poll ignores it). Test `coalesce(sortedAt, createdAt) + 10 min < now()`, and treat attempts=0 as "dispatch in flight" for 1 minute.
- Confidence: CONFIRMED

### R6 [Minor] On phones, an open bucket ⋮ menu in the sheet closes every 4 s while a card is sorting

The proxy guards every `/api/*` route except auth, save and mcp. Pages check the session server-side, and `/setup` renders the secrets only when logged in.
- `/api/mcp` and `/api/save`: bearer and `x-api-key` checks are timing-safe and run before the handler. mcp-handler 2.x doesn't match on path, so mounting it at `/api/mcp` is fine.

- Duplicate check: `normalizeUrl` follows SPEC §5. Concurrent saves are handled by `onConflictDoNothing`. `firstUrl` handles brackets and only matches `http(s)` links, so a `javascript:` href can't get in.
- `pocket_file_item` checks for an owner move inside the UPDATE itself. Owner moves set `sortedBy: owner`. Deleting a bucket is a transactional batch that sets its links to `unsorted` and bumps `sortedAt`.
- Bucket names are unique case-insensitively (409 on a clash). Dismiss only flips open suggestions, and the agent sees dismissed names.
- The migration is explicit SQL, refuses to run twice, keeps the v1 tables as `v1_*`, and seeds the buckets in the spec's order.
- Copy strings, empty states, the `/add` states and timings, and the `/setup` sections match SPEC §3–§4.4. Every page has `noindex`.

Focus rings come from the tokens' terracotta `:focus-visible`, and the CTAs use terracotta. The shadows kept are justified by SPEC tenet 8 ("The current design stays").
